# RAG 复习材料

> 整理自：第 17–20 天学习笔记（RAG 原理 / 闭环 / 切分 / 向量数据库），辅以「学习总览」与「21 周学习计划」。
> 用途：一页看全 RAG 全流程；自测能不看资料讲清楚每个环节。

---

## 一、一句话定义

**RAG = Retrieval-Augmented Generation（检索增强生成）。**

> **先找出相关资料，再让 AI 根据资料回答。**

| 词 | 意思 | 对应哪一步 |
|---|---|---|
| **Retrieval** | 检索 | 找出最相关的几段 |
| **Augmented** | 增强（把资料塞进 prompt） | 拼资料进 prompt |
| **Generation** | 生成（让 AI 基于资料回答） | 发给模型出答案 |

**一句话记住 RAG 的本质：**
> **RAG 把模型从「凭记忆回答」变成「开卷考试」。**
> 开卷考试的学生如果非要凭记忆答题，那还不如不给他书——所以必须用 system 限制它「只看你给的材料」。

---

## 二、RAG 要解决什么问题

大模型的训练数据是**公开数据**，它不知道你的**私人资料**。

你问它「我那份产品手册里写了什么」，它要么说不知道，要么**编一个听起来很像的答案**——这就是「**幻觉**」的主要来源之一：模型不知道自己在瞎编。

### 笨办法：把资料全塞进 prompt（不行）

```
200 页产品手册 + 用户的问题 → 一起发给 AI
```

| 问题 | 说明 |
|---|---|
| **太长** | 超出上下文限制，模型一次能看的字数是有限的 |
| **太贵** | 每次提问都要把整本手册重发一遍 |
| **效果反而差** | 无关信息太多，模型抓不住重点 |

**第三条最反直觉**：给的信息多 ≠ 答得好。**关键信息被淹没在噪音里，模型反而更容易答偏。**

### RAG 的思路

```
用户提问
   ↓
在所有文档里【找出最相关的几段】
   ↓
只把这几段 + 问题 一起发给 AI
   ↓
AI 根据这几段回答
```

**给 AI 的不是「所有资料」，是「跟这个问题相关的那几段」。**
这样：不超长度限制、不贵、效果好（全是相关内容）。

## 四、Step 1 · 切分 Chunking（第 19 天）

**补上 RAG 的第一步：把一篇长文档切成一段一段能检索的小块。**

### 为什么必须先切分

Embedding 一次只能吃一小段文字。整本书喂不进去，原因有三：

| 问题 | 说明 |
|---|---|
| **太长** | 接口对单次输入长度有限制（通常几百到几千 token） |
| **太糊** | 一整章压成一个向量，里面几十个主题全糊在一起，检索时「什么都不像」 |
| **没法定位** | 就算检索到了，也没法把「整章」当成出处贴给用户 |

> **一句话记住：检索的最小单位，就是你切分的最小单位。**
> 你切得不好，检索就不可能好——**后面所有环节的上限，在这里就被定死了。**

### 判断切分好坏的标准

**不是看切得匀不匀、长不长，而是：**
> **拿一个真实问题去搜，该块该不该被搜出来。**

例：一段同时讲「退款天数」和「配送范围」的文字——
整段切成一块 → 向量里混了配送信息，**相似度被稀释，排名靠后**；
拆成两块 → 「退款天数」那块和问题高度匹配，**排名靠前**。

### 三种切法（由简到繁）

| 切法 | 思路 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| **A. 按段落 / 空行切** | `text.split("\n\n")` | 极简单，符合阅读习惯，不切断句子 | 段落长度不可控，超长段落没辙 | 结构规整的文档，**第一步先用它** |
| **B. 按固定字数 + 重叠** | 每 300 字一块，相邻重叠 50 字 | 长度可控，overlap 兜住边界问题 | 可能在句子中间切断，参数要调 | **最常用，必学** |
| **C. 按语义切** | 用模型判断话题是否切换处切 | 语义完整 | 更贵更慢更复杂 | **进阶，现阶段不用做** |

**切法 B 的关键代码：**
```python
def split_by_size(text, chunk_size=300, overlap=50):
    chunks = []
    start = 0
    while start < len(text):
        end = start + chunk_size
        chunks.append(text[start:end])
        start = end - overlap        # 往回退 overlap 字 —— 这就是重叠
    return chunks
```

### ⚠️ 为什么必须重叠（面试会问）

一句话如果正好被切在边界上，**两半各在一块的末尾和开头，哪一块都不完整**：
```
原句：本店规定购买后30天内可以申请全额退款
不重叠切在「30天」中间：
  块1：...本店规定购买后30天
  块2：内可以申请全额退款...     ←「30天内退款」这句意思被劈开了
```
**加了 overlap**，这句话会完整出现在**块1 的后半段**和**块2 的前半段**里——**至少有一块是完整的，检索就能命中。**

### chunk_size 的取舍（重要的不是数字，是这个权衡）

| | 切太小（如 100 字） | 切太大（如 1000 字） |
|---|---|---|
| **好处** | 定位准，向量「纯」 | 上下文完整，不丢信息 |
| **坏处** | 意思不完整，答不出「为什么」 | 主题混杂，向量「糊」，排名差 |
| **症状** | 检索到了，但答案缺一句话 | 排名靠后，甚至搜不到 |

**经典两难**：问「退款要几天」——答案需要「30天」**和**「需提供订单号」两条信息。
切太小 → 两条分在两块，模型只看到一条；
切太大 → 这块混了 5 个主题，相似度被拉低，**根本没被搜出来**。

**实践起步值（先跑起来再调）：**
```
chunk_size = 300   # 字
overlap    = 50    # 字
top_k      = 3     # 检索取前 3 块
```

**调优方向：**

| 现象 | 可能是切分问题 | 怎么调 |
|---|---|---|
| 该搜到的没搜到 | 切太大，主题被稀释 | 调小 `chunk_size` |
| 搜到了但答案不完整 | 切太小，上下文断了 | 调大 `chunk_size` 或 `overlap` |
| 答案出现在块边界 | 没重叠 | 加 `chunk_overlap` |
| 检索结果总是那几块 | 切太粗，块数太少 | 调小 `chunk_size`，让块变多 |

### 真实文档的坑

**⚠️ 顺序：原始文件 → 清洗 → 切分 → 向量化。清洗在切分之前。** 脏文本切出来的块，向量也是脏的。

| 坑 | 现象 | 怎么办 |
|---|---|---|
| **Markdown 标题** | 标题被切成单独一块，没内容 | 标题和正文绑在一起切 |
| **代码块** | 代码被从中间切断，等于废了 | 识别 ``` 区块，整体保留 |
| **表格** | 表格被切散，行列对不上 | 整表保留，或转文字描述 |
| **PDF 提取的换行** | 每行都有 `\n`，按 `\n\n` 切不动 | 先清洗：把单换行合并 |
| **页眉页脚** | 「第 3 章」重复出现在每块里 | 预处理时删掉 |

**PDF「假空行」问题的清洗代码：**
```python
import re
text = re.sub(r"(?<!\n)\n(?!\n)", " ", text)   # 单换行 → 空格
text = re.sub(r"\n{2,}", "\n\n", text)          # 多个空行 → 规范成两个
```

## 五、Step 2 · 向量化 Embedding（第 17 天）

### 关键概念

**把一段文字变成一串数字的过程，叫 embedding（嵌入）；那串数字叫「向量」（vector）。**

| 概念 | 意思 |
|---|---|
| **Embedding** | 动作：文字 → 向量 |
| **向量** | 结果：那串数字 |
| **维度** | 数字的个数（bge-m3 是 **1024 维**） |

**为什么语义搜索要这么做？**
```
"退款"    →  [0.12, -0.83, 0.45, ...]      1024 个数字
"退货"    →  [0.11, -0.79, 0.48, ...]      ← 跟上面很接近
"服务器"  →  [-0.67, 0.22, -0.31, ...]     ← 差很远
```
**含义相近的文字 → 数字串也相近。**（传统关键词搜索搜「退款」只认「退款」两个字，用户问「我买错了想退钱怎么办」就一个字都不重合——RAG 用语义搜索，找意思相近的，不看用词。）

### ⚠️ 三个必须知道的点

1. **同一段文字，每次 embedding 出来的结果是一样的。** 它不像大模型那样有随机性——**同样输入，永远同样输出。**
2. **向量本身没有意义。** `[0.12, -0.83, ...]` 里每个数字代表什么没人能解释，它只是 1024 维空间里的坐标。**你只需关心：两段文字的向量离得近不近。**
3. **不同模型的向量不能混用。** `bge-m3` 和别家模型出来的 1024 维向量是两个不同空间的坐标，放在一起比较毫无意义。**换模型 = 所有数据必须重新向量化。**

### 怎么算「近」—— 余弦相似度

**算两个向量的夹角，越大越像。**

| 结果 | 意思 |
|---|---|
| 接近 **1.0** | 意思几乎一样 |
| **0.5 ~ 0.9** | 相关 |
| 接近 **0** | 基本无关 |
| **负数** | 意思相反（少见） |

**实测参考（bge-m3）：**
| 对比 | 相似度 |
|---|---|
| "想退货怎么办" vs "退款政策：30天内可全额退款" | **0.70** |
| "想退货怎么办" vs "服务器日志保留七天" | **0.50** |

差 0.2，**不算夸张，但排序是对的。RAG 靠的就是这个排序。**

```python
import math

def cosine(a, b):
    dot = 0
    for i in range(len(a)):
        dot += a[i] * b[i]          # 分子：两个向量有多「同向」
    len_a = 0
    for x in a:
        len_a += x * x
    len_b = 0
    for x in b:
        len_b += x * x
    # 相除 = 消掉长度影响，只看方向
    return dot / (math.sqrt(len_a) * math.sqrt(len_b))
```

### 调用 embedding 接口（硅基流动 · 免费 bge-m3）

**DeepSeek 没有 embedding 接口**，需另注册一家。选**硅基流动 siliconflow.cn**：国内不用梯子、`BAAI/bge-m3` 标着免费、接口格式跟 DeepSeek 一样（OpenAI 兼容）。

**⚠️ 最大的坑：域名是 `.cn` 不是 `.com`** → `https://api.siliconflow.cn/v1/embeddings`

```python
import requests

with open("key_sf.txt", encoding="utf-8") as f:
    sf_key = f.read().strip()

def embed(text):
    r = requests.post(
        "https://api.siliconflow.cn/v1/embeddings",
        headers={"Authorization": f"Bearer {sf_key}",
                 "Content-Type": "application/json"},
        json={"model": "BAAI/bge-m3", "input": text},
        timeout=30,
    )
    return r.json()["data"][0]["embedding"]     # 1024 个数字的列表

def embed_batch(texts):
    """批量版：一次请求算多个向量，比循环调用快很多"""
    r = requests.post(
        "https://api.siliconflow.cn/v1/embeddings",
        headers={"Authorization": f"Bearer {sf_key}",
                 "Content-Type": "application/json"},
        json={"model": "BAAI/bge-m3", "input": texts},   # ← 传列表！
        timeout=60,
    )
    return [d["embedding"] for d in r.json()["data"]]
```

**embedding 接口 vs chat 接口的三个区别：**

| | chat 接口 | embedding 接口 |
|---|---|---|
| 网址 | `/chat/completions` | **`/embeddings`** |
| 请求体 | `"messages": [...]` | **`"input": "一段文字"`** |
| 返回值 | `choices[0].message.content` | **`data[0].embedding`** |

**调 API 的套路没变**：读 key → 组装请求 → post → 拿 JSON → 取字段。**只是换了网址、换了字段名。**

**常见报错：**
| 报错 | 原因 | 解决 |
|---|---|---|
| `401` | key 不对 | 检查 `key_sf.txt`，别忘了 `.strip()` |
| 连不上 | 域名写成 `.com` 了 | 改成 `.siliconflow.cn` |
| `404 model not found` | 模型名写错 | 确认是 `BAAI/bge-m3` |
| `402` | 余额不足 | 确认用的是免费模型 |
| `KeyError: 'data'` | 返回结构不对 | `print(response.text)` 看真实内容 |

## 六、Step 3 · 向量数据库 Chroma（第 20 天）

### 为什么要用向量数据库（手写 cosine 的问题）

手写版：`docs` 只有 3 条时没问题，还特别适合理解原理。但换成真实文档（切出 500 块）后：

| 问题 | 说明 |
|---|---|
| **每次搜索都重新算向量** | 500 块 = 调 500 次 embedding。**慢，而且烧钱** |
| **向量没有存下来** | 程序一关全没了，下次从头再来 |
| **纯 Python 循环** | 5 万块就卡死 |
| **没有持久化、没有增删改** | 想加一段文档，得手动改代码 |

> **核心矛盾：向量是「算一次、用很多次」的东西，不该每次搜索都重算。它应该被存起来。**

### 一句话理解

> **普通数据库：按「值」查（`WHERE name = '张三'`）。**
> **向量数据库：按「相似」查（给我离这个向量最近的 5 个）。**

**你手写 cosine = 原理（怎么算「近」）；向量数据库 = 工程（怎么存、怎么快、怎么管）。** 两者不冲突——手写过，所以用 Chroma 时你知道它背后在干什么。

### 四个核心概念（对应手写版）

| 概念 | 是什么 | 对应你手写版 |
|---|---|---|
| **Client** | 数据库连接（本地存一个文件夹） | 内存里的 `docs` 列表 |
| **Collection** | 一个「表」，装一类向量 | 你的 `docs` |
| **Document** | 原始文本 | `doc` |
| **Embedding** | 那串数字 | `embed(doc)` |
| **ID** | 每条的身份证，必须唯一 | 你的 `i` |

**→ Chroma 没有新概念，只是把手写的东西「安了个家」。**

### 完整可用代码骨架

```python
import chromadb

client = chromadb.PersistentClient(path="chroma_db")   # 存硬盘文件夹
collection = client.get_or_create_collection(
    name="my_rag",
    metadata={"hnsw:space": "cosine"},   # 用余弦相似度，和手写一致
)

def build_index(chunks):
    existing = collection.get()["ids"]        # ⭐ 先清空，避免重复 add 翻倍
    if existing:
        collection.delete(ids=existing)
    vectors = embed_batch(chunks)             # 批量算向量（只算一次）
    collection.add(
        ids=[f"chunk-{i}" for i in range(len(chunks))],
        documents=chunks,
        embeddings=vectors,
        metadatas=[{"source": "深度学习入门", "chapter": "第3章"} for _ in chunks],
    )

def search(query, top_k=3):
    result = collection.query(
        query_embeddings=[embed(query)],
        n_results=top_k,
        include=["documents", "distances"],
    )
    docs = result["documents"][0]
    dists = result["distances"][0]
    return [(1 - d, doc) for d, doc in zip(dists, docs)]   # ⚠️ 距离 → 相似度
```

**⚠️ 建议自己算好向量（`embedding_function=None` / 传入 `embeddings`）而不用 Chroma 自带模型**——因为不同模型向量不能混用，统一用 `bge-m3`，手写版和 Chroma 结果才能直接对比。

### ⚠️ 三个必踩的坑

**坑 1：Chroma 返回的是「距离」，不是「相似度」**

| | 你手写 | Chroma |
|---|---|---|
| 返回什么 | 相似度 | 距离 |
| 越大越像？ | ✅ | ❌（越小越像） |
| 换算 | — | **`相似度 = 1 - distance`** |

不换算会以为「排序反了」。

**坑 2：重复 `add` 会让数据翻倍**（`add` 不去重）
症状：检索结果里出现一模一样的块，`top_k=3` 拿回三条全是同一段。
解决：用固定 `ids`（相同 id 覆盖）/ 重建前先 `delete` 清空 / 用 `upsert` 代替 `add`。

**坑 3：持久化 —— 用 `PersistentClient`**
`chromadb.Client()` 存内存（关了就没，适合实验）；`chromadb.PersistentClient(path=...)` 存硬盘文件夹（**正式用这个**）。记得把 `chroma_db/` 加进 `.gitignore`。

### Chroma 带来的能力

| 能力 | 手写版 | Chroma |
|---|---|---|
| 持久化 | ❌ | ✅ |
| 增删改 | ❌ 手动改代码 | ✅ `add`/`delete`/`upsert` |
| 按元数据过滤 | ❌ | ✅ `where={...}` |
| 快（几万块以上） | ❌ 卡 | ✅ 有索引 |
| 批量算向量 | ❌ 循环调接口 | ✅ `embed_batch` |

**⭐ 元数据过滤（Metadata Filtering）——值得单独记：**
```python
collection.query(
    query_embeddings=[embed(query)],
    n_results=3,
    where={"chapter": "第3章"},     # ← 只在第3章里找
)
```
用途：用户问「第 3 章讲了什么」时直接限定章节，**比纯靠相似度更准**——从「带出处的 RAG」升级成「能按来源检索的 RAG」。

### 对比手写版 vs Chroma（面试素材）

同一问题、同一批 chunks，跑两套检索：
| 观察点 | 会看到什么 |
|---|---|
| **排序是否一致** | 通常**基本一致** → 说明你的手写实现是对的 |
| **分数是否一样** | `1 - distance` 后**接近但不完全相同**（浮点精度、库的归一化差异） |

**排序一致 = 你手写的检索逻辑和工业级数据库是同一个东西。**

## 七、Step 4 · 生成 Generation（第 18 天）

**补上后半截：把检索到的资料拼进 prompt，发给 AI，让它基于资料回答。**

### 怎么把资料「塞」进 prompt

就是把它们拼成一段文字，作为 `user` 消息发给模型：
```
请根据下面的资料回答问题。

【资料】
1. 退款政策：购买后30天内可申请全额退款。
2. 配送说明：全国包邮，偏远地区需加收运费。

【问题】
我想退货怎么办？
```

**两个要点：**
1. **「资料」和「问题」必须分开标**（用 `【】`、`====`、`---`）。不标清楚，模型分不清哪句是资料、哪句是问题。
2. **资料要带编号**。编号让模型能说「根据资料 1……」——这就是**出处（引用）**。**带出处的回答，是 RAG 相对普通聊天最大的优势。**

### ⭐ 最关键的一句 system（整个 RAG 里最重要的一段）

```
你是一个客服助手。

只根据下面提供的【资料】回答用户的问题。
如果资料里没有相关信息，就直说「资料里没有提到这个问题」，
不要凭自己的知识回答。
```

**没有这句，RAG 就是白做的。**
模型的训练数据里有一堆「通用知识」，你给了资料它也不一定老实照办——**它会把自己的知识掺进来，甚至完全无视资料，自己编一个**。结果比不做 RAG 更糟——你以为它有依据，实际它在瞎说。

### 为什么非要限制它「不许用自己的知识」

因为**它的大部分训练知识，对具体业务来说是错的**：
```
你给的资料：  本店退款政策：购买后 30 天内可全额退款。
它训练时学的：一般电商是 7 天无理由退货。
不加限制它答：本店支持 7 天无理由退货。  ← 编的，而且很自信
```

**RAG 的目的不是让模型更聪明，是让模型「只看你给的材料」。**

### 完整 `ask()` 流程

```python
def ask(question):
    # ① 检索
    hits = search(question, top_k=3)

    # ② 拼资料（带编号 = 出处）
    context = ""
    for i, (score, doc) in enumerate(hits):
        context += f"{i+1}. {doc}\n"

    # ③ 拼 prompt
    messages = [
        {"role": "system", "content": "只根据【资料】回答，资料里没有就说不知道。"},
        {"role": "user", "content": f"【资料】\n{context}\n【问题】\n{question}"},
    ]

    # ④ 发给大模型
    response = requests.post(
        "https://api.deepseek.com/chat/completions",
        headers={"Authorization": f"Bearer {ds_key}", "Content-Type": "application/json"},
        json={"model": "deepseek-chat", "messages": messages},
        timeout=30,
    )
    return response.json()["choices"][0]["message"]["content"]
```
**④ 跟第 9 天写的完全一样。RAG 没有新 API、没有新库**——就是「先检索，把结果拼进 prompt，再走一遍早就会的流程」。

### 验证 RAG 有没有用（对比着跑）

| 问题 | 不加 RAG | 加了 RAG |
|---|---|---|
| 「你们退款几天内可以」 | 可能答「7天」（编的） | 答「30天」（根据资料） |
| 「你们支持货到付款吗」 | 编一个 | **说「资料里没有提到」** |

**第二种情况最关键——它承认自己不知道。**
> **这才是 RAG 的价值：不是答得更好，是「不知道就说不知道」。**

### 常见问题排查

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 模型无视资料，自己编 | system 里没写「只根据资料」 | 加那句限制 |
| 模型把资料和问题搞混 | 没分开标记 | 用【】分隔清楚 |
| 资料明明有，它说没有 | 检索没检索到（召回问题） | 调大 `top_k`，或改检索方式 / 检查切分 |
| 答对了但不给出处 | system 里没要求 | 加「回答时注明根据哪条资料」 |

**拼接方式选择：** 推荐把资料放在 `user` 消息（方式 A），因为**每次提问的资料不一样**，它属于「这一次的输入」，不该放进 system（system 是长期设定）。

## 八、自测清单（不看资料，能讲清楚吗）

**切分（19）**
1. 为什么要切分？—— embedding 输入有长度限制；整篇压成一个向量会「糊」；**检索的最小单位 = 切分的最小单位**。
2. `chunk_overlap` 干什么的？—— 防止句子被切在边界上，让跨边界的关键句至少完整出现在一块里。
3. 切大 / 切小各错在哪？—— 切小：上下文断，答案不完整；切大：主题混杂，向量被稀释，检索排名差。
4. 真实文档切分前要先做什么？—— **清洗**（PDF 假换行、页眉页脚、代码块保护），再切。
5. 怎么判断切分好不好？—— 不是看匀不匀，**是拿真实问题去搜，看该出来的是不是出来了**。

**向量（17）**
6. embedding / 向量 / 维度分别指什么？
7. 为什么不同模型的向量不能混用？换模型要做什么？
8. 余弦相似度多大算像？为什么它比关键词搜索强？

**向量库（20）**
9. 为什么不一直用手写的 `cosine`？—— 向量该「算一次用多次」；手写版每次搜索都重算、不持久化、量大就慢。
10. Chroma 返回的距离 vs 相似度？—— `cosine` 空间下 `distance = 1 - 相似度`，越小越像。
11. `add` 和 `upsert` 的区别？—— `add` 重复会翻倍，`upsert` 有则更新；固定 id 也能避免翻倍。
12. 元数据过滤有什么用？—— 用已知信息（来源/章节/日期）缩小范围，比纯相似度更准。
13. Chroma 帮你解决了什么你自己解决不了的？—— **持久化、增删改、过滤、索引速度**。

**生成（18）**
