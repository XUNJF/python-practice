# 第 20 天学习笔记 · Chroma 向量数据库

> 补上第 16 天空缺的一课：**把切好的块存进向量数据库，用它替代你手写的 `cosine` 搜索。**
> 这是成都/杭州 JD 里的高频关键词（向量数据库 10+ 次），也是「RAG 从 demo 变成工程」的分界线。

---

## 一、你手写的检索，问题在哪

第 17 天的做法：

```python
def search(query, top_k):
    v_q = embed(query)
    scores = []
    for doc in docs:               # ← 每个文档都要调一次 embedding
        scores.append((cosine(v_q, embed(doc)), doc))
    scores.sort(reverse=True)
    return scores[:top_k]
```

**`docs` 只有 3 条时，完全没问题，还特别适合理解原理。**
但换成真实文档（切出 500 块）之后，问题就来了：

| 问题 | 说明 |
|---|---|
| **每次搜索都重新算向量** | 500 块 = 调 500 次 embedding 接口。**慢，而且烧钱** |
| **向量没有存下来** | 程序一关，全没了，下次从头再来 |
| **纯 Python 循环** | 500 块还行，5 万块就卡死 |
| **没有持久化、没有增删改** | 想加一段文档，得手动改代码 |

**核心矛盾：**
> 向量是「算一次、用很多次」的东西，**不该每次搜索都重算。**
> **它应该被存起来。**

**向量数据库就是干这个的。**

---

## 二、⭐ 一句话理解向量数据库

> **普通数据库：按「值」查（`WHERE name = '张三'`）。**
> **向量数据库：按「相似」查（给我离这个向量最近的 5 个）。**

它专门优化了一件事：**在几万、几百万个向量里，快速找出「离目标最近的几个」。**

**你手写 `cosine` 是对的方向，只是：**
> **你写的 = 原理（怎么算「近」）**
> **向量数据库 = 工程（怎么存下来、怎么快、怎么管）**

**两者不冲突——你手写过，所以用 Chroma 时你知道它背后在干什么。这个顺序是对的。**

## 三、装 Chroma

```bash
pip install chromadb
```

**⚠️ 一个取舍：Chroma 本地版默认自带 embedding 模型**（会下载一个 sentence-transformers 模型）。
但**建议你继续用硅基流动的 `bge-m3`**——因为：

1. **不同模型的向量不能混用**（第 17 天讲过）。你之前的数据都是 `bge-m3` 的，
2. 换模型 = 数据全废，检索结果会莫名其妙变差。
3. 统一用 `bge-m3`，你手写的和 Chroma 的结果**可以直接对比**。

**所以做法是：自己算好向量，再存进 Chroma。**（用 `embedding_function=None` 关掉它自带的）

---

## 四、四个核心概念

| 概念 | 是什么 | 对应你手写版 |
|---|---|---|
| **Client** | 数据库连接（本地就是存一个文件夹） | 内存里的 `docs` 列表 |
| **Collection** | 一个「表」，装一类向量 | 你的 `docs` |
| **Document** | 原始文本 | `doc` |
| **Embedding** | 那串数字 | `embed(doc)` |
| **ID** | 每条的身份证，必须唯一 | 你的 `i` |

**记住这个映射，你会发现 Chroma 没有新概念，只是把手写的东西「安了个家」。**

## 五、完整可跑的代码

```python
import chromadb
import requests

# ---- 0. 读 key ----
with open("key_sf.txt", encoding="utf-8") as f:
    sf_key = f.read().strip()


def embed(text):
    """沿用你第 17 天写的，一个字都不用改"""
    r = requests.post(
        "https://api.siliconflow.cn/v1/embeddings",
        headers={"Authorization": f"Bearer {sf_key}",
                 "Content-Type": "application/json"},
        json={"model": "BAAI/bge-m3", "input": text},
        timeout=30,
    )
    return r.json()["data"][0]["embedding"]


def embed_batch(texts):
    """批量版：一次请求算多个向量，比循环调用快很多"""
    r = requests.post(
        "https://api.siliconflow.cn/v1/embeddings",
        headers={"Authorization": f"Bearer {sf_key}",
                 "Content-Type": "application/json"},
        json={"model": "BAAI/bge-m3", "input": texts},   # ← 传列表！
        timeout=60,
    )
    data = r.json()["data"]
    # 返回的顺序和输入一致，直接取出来
    return [d["embedding"] for d in data]


# ---- 1. 连接（数据存在 ./chroma_db 文件夹）----
client = chromadb.PersistentClient(path="chroma_db")

# ---- 2. 建/取出一个 collection ----
# get_or_create：有就取出，没有就新建（重复跑不会报错）
collection = client.get_or_create_collection(
    name="my_rag",
    metadata={"hnsw:space": "cosine"},   # ← 用余弦相似度（和你手写的一致）
)


def build_index(chunks):
    """把第 19 天切好的块，存进 Chroma"""
    # ⭐ 先清空，避免重复跑时数据翻倍
    existing = collection.get()["ids"]
    if existing:
        collection.delete(ids=existing)

    vectors = embed_batch(chunks)          # 批量算向量（只算一次！）

    collection.add(
        ids=[f"chunk-{i}" for i in range(len(chunks))],
        documents=chunks,                   # 原文
        embeddings=vectors,                 # 向量
    )
    print(f"已存入 {len(chunks)} 块")


def search(query, top_k=3):
    """检索：和手写版返回格式一致 [(分数, 文档), ...]"""
    result = collection.query(
        query_embeddings=[embed(query)],
        n_results=top_k,
        include=["documents", "distances"],
    )
    docs = result["documents"][0]
    dists = result["distances"][0]
    # ⚠️ Chroma 返回的是「距离」，不是相似度！要转一下
    return [(1 - d, doc) for d, doc in zip(dists, docs)]


if __name__ == "__main__":
    # chunks 来自第 19 天的切分结果
    from day19_split import split_doc
    chunks = split_doc("深度学习入门.txt", chunk_size=300, overlap=50)

    build_index(chunks)
    for score, doc in search("什么是感知机", top_k=3):
        print(f"\n{score:.4f}  {doc[:60]}...")
```

## 六、⚠️ 三个必踩的坑

### 坑 1：Chroma 返回的是「距离」，不是「相似度」

**最容易懵的地方。** 你手写的 `cosine` 是**越大越像**（1.0 = 一样）。
Chroma 在 `cosine` 空间下返回的 `distance` 是 **`1 - 余弦相似度`**，**越小越像**。

| | 你手写 | Chroma |
|---|---|---|
| 返回什么 | 相似度 | 距离 |
| 越大越像？ | ✅ | ❌（越小越像） |
| 换算 | — | `相似度 = 1 - distance` |

**所以对比结果时要换算，否则会以为「排序反了」。**

### 坑 2：重复 `add` 会让数据翻倍

**Chroma 的 `add` 不会去重**——同样的内容 `add` 两次，就是两份。

**症状**：检索结果里出现**一模一样的块**，`top_k=3` 拿回来三条全是同一段。

**解决**：
- 用固定的 `ids`（比如 `chunk-0`、`chunk-1`）——**相同 id 会覆盖，不会翻倍**
- 或者每次重建前先 `collection.delete(...)` 清空（上面代码就是这么做的）
- 或者用 `collection.upsert(...)` 代替 `add`（有则更新，无则新增）

### 坑 3：持久化 —— `PersistentClient` vs `Client`

| | 数据存哪 | 什么时候用 |
|---|---|---|
| `chromadb.Client()` | **内存**，关了就没了 | 一次性实验 |
| `chromadb.PersistentClient(path=...)` | **硬盘上的文件夹** | **正式用这个** |

**用 `PersistentClient`**，你会看到目录里多出一个 `chroma_db/` 文件夹——**这就是「向量数据库」实体。**
**记得把 `chroma_db/` 加进 `.gitignore`**（数据不入库，只传代码）。

## 七、和手写版对比（这是今天最有价值的一步）

**同一个问题，分别用 `day17` 的手写 `search()` 和 Chroma 的 `search()` 跑，对比：**

```python
# 手写版
v_q = embed(question)
manual = sorted([(cosine(v_q, embed(c)), c) for c in chunks], reverse=True)[:3]

# Chroma 版
chroma_hits = search(question, top_k=3)
```

**观察两件事：**

| 观察点 | 会看到什么 |
|---|---|
| **排序是否一致** | 通常**基本一致**——说明你的手写实现是对的 |
| **分数是否一样** | `1 - distance` 后**接近但不完全相同**——浮点精度、库的归一化差异 |

**如果排序一致 —— 恭喜，你手写的检索逻辑和工业级数据库是同一个东西。**
**这个对比，本身就是面试里能讲的一段话**（尤其是杭州那种要你「讲清楚为什么」的岗位）。

## 八、Chroma 还给你带来了什么

**这是「为什么要用数据库」而不只是「它更快」的答案：**

| 能力 | 手写版 | Chroma |
|---|---|---|
| 持久化（关程序不丢） | ❌ | ✅ |
| 增删改（加一段新文档） | ❌ 手动改代码 | ✅ `add` / `delete` / `upsert` |
| 按元数据过滤 | ❌ | ✅ `where={"source": "第3章"}` |
| 快（几万块以上） | ❌ 卡 | ✅ 有索引 |
| 批量算向量 | ❌ 循环调接口 | ✅ `embed_batch` 一次请求 |

**⭐ 元数据过滤（Metadata Filtering）是个宝藏功能，值得单独记：**

**存的时候带上 `metadata`：**

```python
collection.add(
    ids=[f"chunk-{i}" for i in range(len(chunks))],
    documents=chunks,
    embeddings=vectors,
    metadatas=[{"source": "深度学习入门", "chapter": "第3章"} for _ in chunks],
)
```

**查的时候就能限定范围：**

```python
collection.query(
    query_embeddings=[embed(query)],
    n_results=3,
    where={"chapter": "第3章"},     # ← 只在第3章里找
)
```

**用途**：用户问「第 3 章讲了什么」时，可以直接限定章节，**比纯靠相似度更准**。
**这就是「带出处的 RAG」升级成「能按来源检索的 RAG」。**

## 九、验收标准（自测）

**不看资料，能讲清楚：**

1. **为什么不一直用手写的 `cosine`？** —— 向量该「算一次用多次」，手写版每次搜索都重算、不持久化、量大就慢。
2. **Chroma 里返回的距离 vs 相似度？** —— `cosine` 空间下 `distance = 1 - 相似度`，越小越像，**别以为排序反了**。
3. **`add` 和 `upsert` 的区别？** —— `add` 重复会翻倍，`upsert` 有则更新。固定 id 也能避免翻倍。
4. **元数据过滤有什么用？** —— 用已知信息（来源、章节、日期）缩小检索范围，比纯相似度更准。
5. **Chroma 帮你解决了什么你不能自己解决的？** —— 持久化、增删改、过滤、索引速度。
